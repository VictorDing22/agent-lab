## 任务 2：逐行读懂 chat.py

### 1. `messages` 里 system / user / assistant 三种角色各起什么作用？

`messages` 是发给模型的整份对话状态，每条都是 `{"role": "...", "content": "..."}`。

| 角色 | 谁说的 | 作用 |
|---|---|---|
| **system** | 开发者设定 | 人设与全局规则。如“你是采购助手、不确定别编造”。通常放数组最前面，整场对话持续生效。 |
| **user** | 用户 | 用户这一轮输入的问题/指令。 |
| **assistant** | 模型自己 | 模型上一轮（或更早）的回答。必须写回历史，否则下一轮它看不到自己说过什么。 |

对应代码：

```python
messages = [{"role": "system", "content": SYSTEM_PROMPT}]  # 启动时放人设
messages.append({"role": "user", "content": user_input})   # 用户说话
# ... 模型回答 ...
messages.append({"role": "assistant", "content": "".join(reply_parts)})  # 模型回答写回
```

一句话：**system 定规矩，user 提问题，assistant 记答案；三者合在一起才是完整对话。**

### 2. 为什么每次请求都要把整个 `messages` 历史发过去？

因为**模型本身是无状态的（stateless）**。

- 它不会在服务器里“记住上次聊过什么”。
- 每次 `create(...)` 只看到你这次请求里带的 `messages`。
- 所谓“有记忆”，全是你的程序把历史拼好再整包重发。

如果改成只发最后一句 user：

```python
# 错误示范：只发最后一句 → 模型失忆
stream = client.chat.completions.create(
    model=MODEL,
    messages=[{"role": "user", "content": user_input}],  # 没有历史
    stream=True,
)
```

现象：你上一轮说“我叫老王”，下一轮问“我是谁”，它答不上来——因为历史没带过去。

所以代码里必须是：

```python
messages=messages  # 整份历史
```

### 3. 流式输出的 chunk 是什么结构？

`stream=True` 时，接口不是一次返回整段话，而是连续返回很多小包 `chunk`。

每个 chunk 大致长这样（字段示意）：

```json
{
  "id": "chatcmpl-xxx",
  "object": "chat.completion.chunk",
  "created": 1730000000,
  "model": "qwen3:8b",
  "choices": [
    {
      "index": 0,
      "delta": {
        "role": "assistant",   // 通常只在第一个包出现
        "content": "你"        // 这一小步新生成的文字；也可能是 null
      },
      "finish_reason": null    // 结束时变成 "stop"
    }
  ]
}
```

代码里真正用到的是：

```python
delta = chunk.choices[0].delta.content or ""
```

- `choices[0]`：第一个候选（一般就一个）
- `delta.content`：这一瞬间新增的字；没有内容时可能是 `None`，所以用 `or ""`
- 循环把每个 `delta` 拼起来，才得到完整回答

和“非流式”对比：非流式一次拿到完整 `message.content`；流式是很多 `delta.content` 拼出来。

## 验收标准口述题

### 模型为什么显得有记忆？

可以这样口头讲：

> 模型本身没有记忆。每次请求只看你发给它的 messages 数组。  
> 我们的程序把 system、历次 user、历次 assistant 都攒在这个数组里，  
> 下一轮提问时整包再发一遍，所以它看起来“记得上文”。  
> 少发历史就会失忆；数组越堆越长，就会撞上下文窗口上限。

## 思考题

### 1. 采购员连续问 500 轮，会发生什么问题？有哪些解决办法？

**会发生的问题：**

1. **上下文窗口爆掉**：messages 总 token 超过模型上限 → 报错或被截断  
2. **越来越慢**：每轮都重发全部历史，计算量随轮数涨  
3. **本地更吃内存**：长上下文占更多统一内存  
4. **早期信息被淹没**：历史太长时，模型更容易忽略开头的关键事实  
5. **（云端时）费用暴涨**：本地无按 token 计费，但真项目接商用 API 会很贵  

**解决办法（联系真项目会话态管理）：**

| 办法 | 做法 | 本练手营对应 |
|---|---|---|
| 滑动窗口 | 只保留最近 N 轮 | 可自己先改 chat.py 试 |
| 上下文压缩 | 旧对话总结成摘要再替换 | 第 5 关 |
| 长期记忆 | 重要身份/偏好写入文件，不必每轮塞全文 | 第 5 关 `memory.md` |
| 会话落库 | Chat 历史存数据库，按会话 ID 加载 | 真项目 Agent 会话态 |
| RAG 外置知识 | 制度/资料不塞对话里，需要时再检索 | 第 6 关 |

真项目不会让一个会话无限膨胀，通常是：**短期窗口 + 压缩摘要 + 必要长期记忆 + 知识库检索**。

### 2. “回答要引用制度条款”写在 system 里 vs 写在 user 里，效果一样吗？

**结论：不一样，通常写在 system 里更稳。**

| 放哪里 | 特点 |
|---|---|
| **system** | 全局规则，整场对话持续约束；用户换话题后规则仍在。适合“人设、合规要求、回答格式”。 |
| **user** | 只对这一轮（或紧挨着的上下文）影响大；后面轮次若不再重复写，约束容易变弱。适合“这一题的具体要求”。 |

**建议实验（你本机可复现）：**

1. system 写：`回答必须引用制度条款；不确定就说需要核实，不要编造。`  
   user 只问：`单一来源超过多少钱要专家论证？`  
   → 观察是否更常出现“依据/条款/需核实”这类合规口吻。

2. system 只写：`你是助手。`  
   user 写：`回答要引用制度条款……单一来源超过多少钱要专家论证？`  
   → 这一轮也可能遵守，但接着再问一个无关问题（如“你好”），system 版仍保持合规口吻，user 版更容易丢掉这条规则。

**实务建议：**

- 长期有效的规矩 → 放 **system**（如本关 `SYSTEM_PROMPT`）  
- 只针对当前问题的补充 → 放 **user**  
- 重要合规要求两边都写也可以，但以 system 为主更稳妥  

注意：这一关还没有制度知识库，模型就算说“引用条款”，也可能在编——真引用要等第 6 关 RAG。

## 本关三句话总结

1. 模型无状态；记忆 = 每次整包重发 `messages`。  
2. system 定规矩，user 提问题，assistant 记答案。  
3. 流式 = 很多带 `delta.content` 的 chunk 拼成完整回答；长对话要用窗口/压缩/记忆来管。
